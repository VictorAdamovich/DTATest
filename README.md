# Менеджер задач

Приложение для управления списками задач: дедлайны, приоритеты, прогресс и подсветка просрочек.

- Живое демо: https://task-manager-production-c39b.up.railway.app
- Демо-доступ: `admin@example.com` / `Admin123!`

Данные на демо-стенде живут в памяти сервера и сбрасываются к исходному набору при перезапуске —
это ожидаемое поведение, подробнее в разделе [«Как устроен слой данных»](#как-устроен-слой-данных).
Локальный запуск описан ниже.

## Запуск

```bash
npm ci
npm run dev          # http://localhost:3000
npm run storybook    # http://localhost:6006
```

Требуется Node.js 22.

Переменные окружения не обязательны; для продакшена задайте `SESSION_SECRET` (см. `.env.example`).

## Как устроен слой данных

Источник правды — серверный in-memory стор (`src/server/db`), спрятанный за интерфейсами
репозиториев (`src/server/repositories`). Он живёт только в памяти процесса: все списки и задачи
сбрасываются к сидовым данным при каждом перезапуске сервера — это ожидаемое поведение демо-стенда,
а не баг. Контроллеры (`src/server/controllers`) валидируют вход Zod-схемами, вызывают репозитории и
отдают DTO. У контроллеров два входа:

- **Чтение для страниц — в React Server Components.** `app/(main)/lists/page.tsx` и
  `app/(main)/lists/[id]/page.tsx` проверяют сессию, вызывают контроллеры напрямую и передают
  результат в кэш TanStack Query через `HydrationBoundary`. Страница приходит из сервера уже с
  данными, а после гидратации повторного запроса нет. Смена `?q=` или `?status=` перерисовывает
  серверную страницу, и новые данные приходят в том же RSC-ответе.
- **Мутации — через `app/api/*`.** Тонкие роут-хендлеры вызываются из клиентских компонентов (формы,
  модалки, выбор статуса) через `apiFetch` и мутации TanStack Query с оптимистичными обновлениями.
  Перезапрос данных после мутации тоже идёт через эти ручки.

Сессия проверяется рядом с каждым чтением данных, а не только в layout: сегменты App Router
рендерятся независимо, и guard в layout не защищает данные страницы. Клиентские компоненты никогда
не импортируют `src/server` — это проверяет линтер.

Доменные правила — чистые функции в `src/entities/*/model`: `sortTasks`, `computeListStats`,
`isOverdue`, `isDueSoon`, `filterTasks`. У каждой из них одна реализация независимо от того, кто её
вызывает — но сегодня вызывающие разные: `sortTasks`, `computeListStats` и `filterTasks` используются
только серверными контроллерами (сортировка и агрегаты считаются на сервере и приходят клиенту уже
готовыми), а `isOverdue`/`isDueSoon` вызываются и на сервере, и на клиенте — ими подсвечиваются
просроченные и близкие к дедлайну задачи прямо в UI. Все функции принимают `now` параметром и
полностью покрыты тестами.

Замена хранилища на реальную БД затрагивает только `src/server/db` и `src/server/repositories`.

## Архитектура (FSD)

`app → views → widgets → features → entities → shared`; импорт вверх по слоям запрещён и
проверяется линтером. Роутинг вынесен в корневой `app/`, чтобы слои не зависели от фреймворка.

## Тесты

```bash
npm test              # юнит-тесты домена и сервера (Vitest)
npm run test:storybook # interaction-тесты историй с play
npm run test:all      # всё сразу
```

`test:storybook` и `test:all` запускают Storybook-тесты в настоящем Chromium через Playwright.
Один раз после `npm ci` установите браузер:

```bash
npx playwright install chromium
```

Покрыто: сортировка задач, агрегаты карточки списка, правила просрочки, фильтрация, репозитории,
контроллеры API, схемы валидации. В Storybook — интеракционные тесты логина, валидации форм,
смены статуса (включая откат при ошибке сервера), переключения темы, поиска и редактирования задачи.
